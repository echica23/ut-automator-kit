# 設計メモ

- 機能はcoverage/spec/review。段階や順序に依存しない。
- AIは対象解決、ケース設計、生成、仕様照合、レビュー、作業時間の記録を担当。スクリプトはフォルダ分離、ハッシュ、Maven呼出し、結果集計を担当。
- spec/reviewの生成処理は共通ルール。reviewでは分析が増える。独立生成の完全一致は保証しない。
- 既存UTとの混在を避けるため、導入時にtestSourceDirectoryを既定値維持のプロパティに変更。通常ビルドは従来どおり。生成実行では別ルートを渡す。
- 出力はユーザー指定先に機械出力とAIレポートをまとめる。実行IDは日時＋ランダムID。既存結果を再利用せず上書きしない。
- 保護対象は実行前後の全ファイル集合とハッシュで比較。新規ファイルも検出。読み取り専用の強制機構ではなく、変更検出である。
- 設定済みMavenプロファイルは信頼境界。Mavenプラグインの任意コード実行をサンドボックス化するキットではない。未知のプロジェクトは導入調査が必要。
- ログ・XMLには環境パスやテスト入力が含まれ得る。Git操作と公開は人間が手動で行い、AIは代行しない。実データをUTに埋め込まない。
- カバレッジ集計の対象は完全修飾クラスの一致。非標準ソース、内部クラス、集約レポートは初版の自動解決対象外。
- 実行スクリプトは生成/推論を行わない。AI最終レポート完了はsummary.jsonで自動的にtrueにしない。

今後の拡張候補（初版に含まない）: リアクタ全体、Gradle、既存生成UTの明示再利用コマンド、CI/API経由のモデル使用量取得、モデル別費用換算。


仕様参照はファイル/ディレクトリを許可する。ディレクトリの全配下ハッシュは変更検出用であり、本文の一括読込みではない。AIは対象との関連性で資料を選び、report.mdに参照根拠を残す。

coverageは実装解析に基づく固定期待値を事前に決め、実行結果から期待値を作る自己比較を禁止する。spec/reviewの期待値未確定はSPEC_UNKNOWNとしてreport.mdで実行結果と分けて記載し、生成可能なケースは継続する。機械集計のテスト状態と仕様評価の未確定状態を混同しない。

Project Rulesは任意のファイル配列としてプロジェクト設定に登録する。スクリプトが参照先と
ハッシュを記録・保護し、AIが関連節を選択してテスト方針へ適用する。
業務期待値の根拠とは分離し、SPEC_UNKNOWN原則は維持する。
優先順位、矛盾・除外の扱い、適用証跡は [Project Rulesの設計](project-rules.md) に定義する。

## 出力と読込みの簡素化

人間向け説明は全モードでreport.mdに集約する。成功は集計し、FAIL/ERROR/SKIP、
SPEC_UNKNOWN/RULE_CONFLICT、未カバー・未計測・除外を個別に記載する。
reviewは同じ指摘に原因・位置・確度・修正案を追加する。
仕様対応はUTコメントで保持し、成功ケースの一覧をレポートに再掲しない。

AIによるspec-sources.json、spec-unknown.json、rules-application.json、review.md、
token-usage.jsonは新規生成しない。機械生成のexecution.mdも廃止する。
run.json/project-rules.json、ハッシュ、summary.json/case-results.json、ログ、
Surefire/JaCoCo、生成UTは実行・保護・検証に必要な証跡として保持する。
過去の出力を移行・削除する処理は追加しない。設定schemaVersion=1を維持する。

summary.json/change-check.json/case-results.jsonを最初の確認に使い、問題の詳細・
未カバー箇所・集計の不整合がある場合に該当する元XML/ログを確認する。
成果物全体の繰り返し読込みは要求しない。CDATA出力もcase-results.jsonへ本文を保存する。
テストの網羅方針、固定ID、仕様の根拠、安全制約、正当なFAILの扱いは維持する。

Copilotを職場の利用対象として想定し、特定エージェントの内部ログやトークン取得機能に依存しない。
共通プロンプトとPowerShell実行を利用し、製品専用の呼出し機構は追加しない。
作業時間はAIが時計で境界を取得し、Maven時間はスクリプトのStopwatchで測定する。
詳細な計測区間・未取得の扱いは実行プロンプト、項目はスクリプト仕様を参照。
クラス数は要求・実行確認済み・未実行を分け、テストクラス数から推定しない。

この削減が実行時間をどれだけ短縮するかは未検証。Copilotで同じ対象・モデル・
ケース範囲を使って比較する必要がある。コンテキスト再利用は引き続き将来案である。
## Javadocによる契約参照

spec/reviewは-D資料または-J契約を明示選択し、併用・自動切替はしない。
ケース単位で期待値を確定し、不足はSPEC_UNKNOWNとして部分継続する。
実装やProject Rulesで補完しない。根拠と保証範囲はreport.mdに集約する。
選択・参照・保護・互換性の詳細は[Javadocモード](javadoc-mode.md)を参照。

-JではJavadocを第一、通常コメントの明確な現在の契約を補助根拠とする。
処理手順・TODO等は採用しない。期待結果に影響する契約矛盾はケース単位で
SPEC_UNKNOWNとし、JUnitのskipにせず、影響しないケースは継続する。
意味解析はAIの責務であり、specSource=javadocと両ランナーの処理は維持する。
詳細は[Javadocモード](javadoc-mode.md)、例は[記述ガイド](javadoc-guide.md)を参照。

## PowerShell 5.1／7対応

実行基盤を両ホストで共通化する。スクリプトはUTF-8 BOM付き、
JSON/生成Javaの読込みはUTF-8明示、JSON出力はBOMなしUTF-8。
XMLは文字コード宣言に従い、改行正規化と外部DTD参照の抑止を共通化する。
Mavenのstderrと終了コードを分けて扱い、正当なFAIL後もJaCoCoを実行する。
Java/JaCoCo等の版選定は導入時に行い、UT実行中の自動更新はしない。

## 実行基盤の選択

新規はJava版、PowerShell版は継続利用可能。runner省略の既存設定はpowershell。
設定・出力の意味・保護ルールを共通化し、失敗時の自動切替はしない。
Java版を利用者のプロジェクト依存へ組み込まず、独立した依存同梱JARとして配布する。
参照: [実行基盤の共通契約](runner-spec.md)。本書の既存「スクリプト」の責務は
Java版にも同じく適用する。UT生成・業務判断は引き続きAI側である。
