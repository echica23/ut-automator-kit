# 将来拡張案：コンテキスト再利用による実行効率改善

**状態：将来検討中・現在は未実装。** 本文は設計アイデアであり、導入・実行指示や確定仕様ではない。現行のコマンド、設定、出力先、スクリプトの動作は変更しない。

## 背景と目的

UTの再実行では、対象ソース・依存クラス・仕様書・ビルド設定を再解析する可能性がある。解析済みのコンテキストを中間成果物として保存し、変更のない部分を再利用することで、次の改善を目指す。

- 再実行時のInput Tokenと、不要なソース・仕様書の再読込みを減らす。
- UT側の問題を絞って修正し、不要なMaven実行や試行錯誤を減らす。
- 大規模プロジェクトやwildcard指定時の処理効率・スケーラビリティを改善する。
- 処理の進行状況と、障害が発生したフェーズを見えるようにする。
- 処理時間・トークン量・実行回数を基に性能とコストを評価する。

コンテキストを保存するだけでMaven実行回数が減るとは限らない。再解析・再生成・再実行の範囲を適切に絞れるかも含めて効果を検証する。

## 処理分離の案

```text
DISCOVERY → GENERATION → EXECUTION → REPAIR
                              ↑         │
                              └─────────┘
```

REPAIRはUT側の問題がある場合にだけ行う。前提となるコンテキストに変更や不足があれば、必要な範囲でDISCOVERYへ戻る。

ここでいうフェーズは、各コマンド内部の処理を整理するための概念である。coverage → spec → reviewという実行順序を設けるものではなく、現行の3モードの独立性を維持する。

### DISCOVERY：生成に必要なコンテキストの確定

対象クラス、依存関係、関連仕様、ビルド設定、適用するProject Rulesなどを解析し、生成に必要な情報と参照根拠を整理する。その結果を保存し、後続フェーズや再実行で再利用する。

wildcard指定では具体的な対象一覧を確定し、共通の依存・仕様とクラス固有の情報を分けて扱うことを検討する。全資料を毎回コンテキストへ投入することは目的としない。

### GENERATION：確定したコンテキストによるUT生成

原則としてDISCOVERYの結果を入力にUTを生成する。毎回ソース・仕様書全体を探索し直さず、情報が不足する場合だけ参照元を確認する。

要約を業務仕様の代替となる正解として扱わず、期待値の根拠を元の仕様箇所へ追跡できるようにする。coverageとspec/reviewの期待値の決め方は現行ルールを維持する。

### EXECUTION：UT実行と結果収集

生成UTをMaven/JUnit/JaCoCoで実行し、テスト結果、カバレッジ、失敗内容を収集する。結果を対象・生成UT・実行IDと対応付け、REPAIRへ渡す。

現在の実行スクリプトや機械集計を活用する方向で検討するが、既存成果物との対応やファイル構成は未決定とする。

### REPAIR：UT側の問題に限定した修正

失敗したテストと関連する実装・仕様を中心に、必要な箇所だけ再解析する。UTのコンパイル不備、Mock設定、テスト準備等の問題を修正し、再実行する。

仕様と実装の不一致による正当なFAILは修正対象にしない。本番コードの変更、期待値の実測値への置換、skipによるFAILの隠蔽は行わない。環境・導入設定の問題もUTの不備と混同せず分類する。

失敗原因を断定できない場合は追加確認の範囲を広げる。局所的な修正が他のケースへ影響し得る場合には必要な回帰確認を行い、実行回数の削減だけを優先しない。

## 中間成果物のイメージ

以下は将来の配置例であり、現在このディレクトリやファイルを自動生成する機能はない。

```text
.ut-automator/
  work/
    FooService/
      context.json       # 対象・参照元・解析条件
      spec-summary.md    # 関連仕様の要約と元資料への参照
      dependencies.json # 依存関係とテストに必要な情報
      test-result.json  # 実行結果・失敗内容
      coverage.json     # 計測結果
```

ファイル名・形式・保存先は未確定。現行のoutputRoot／-Oや実行ID別成果物との関係、同名クラス・複数モジュール・モード・試行の識別方法を別途検討する。上記のFooServiceという単純な名前だけを保存キーとして確定しない。

解析コンテキストの再利用と、古いUT・実行結果の再利用は区別する。現行の新規実行IDによる再試行と過去成果物の保持を維持し、古いテスト結果やカバレッジを今回の実測結果として扱わない。

## 再利用時に維持する原則

- ソース、依存関係、仕様、ビルド設定、Project Rules、キットの生成方針が変わった場合の無効化・再解析を検討する。ハッシュや参照関係による判定が候補となる。変更影響を判定できない場合は再解析する。
- 保存する情報には参照元と解析範囲を残す。仕様ディレクトリ内の追加・削除やwildcard対象の変化も考慮し、過去に読んだファイルだけの一致で再利用可と断定しない。
- spec/reviewの業務期待値の根拠は-Dの仕様とする。Project Rulesはテスト方法を定め、仕様不足を実装や保存済み要約で補完しない。SPEC_UNKNOWNやRULE_CONFLICTを再利用によって消さない。
- coverageは実装解析に基づく固定期待値を使用し、過去のspec/reviewの期待値を無条件に流用しない。
- 本番コード・既存UTの保護、private methodの直接テスト禁止、導入先でのGit操作禁止など、既存の安全制約を維持する。

## フェーズ別の計測案

各フェーズと試行を識別し、次の値を取得可能な範囲で記録することを検討する。

| 指標 | 評価したいこと |
| --- | --- |
| 処理時間 | 再解析・生成・実行・修正のどこに時間がかかるか |
| Input Token | コンテキスト再利用で入力がどれだけ減ったか |
| Output Token | 中間成果物・UT・分析の出力負担 |
| AI iteration数 | 生成・修正に必要な反復回数 |
| Maven実行回数 | 再試行や計測を含む実行負担 |

AI iterationの数え方、Mavenのtestとjacoco:reportの区別、計測区間と再試行の集計方法は未決定。トークンのフェーズ別取得も実行環境に依存し、取得不能な値をゼロや正確な実測値として扱わない。現行の概算計測を超える精度は保証しない。

初回実行とコンテキスト再利用時を、同じ対象・モード・テスト範囲で比較する。品質や網羅範囲の低下による見かけ上の削減を避け、保存・検証の追加コストも含めて評価する。
