# Javadocを根拠とするspec/review

## 選択と責務

spec/reviewで-Dの代わりに-Jを明示指定する。併用・両方省略は禁止。
coverageには-Jを指定できない。Javadocがない場合も実装や別の資料へ自動切替しない。
specは契約と実測の不一致まで、reviewは原因・箇所・確度・修正案まで扱う。
UT生成方針は両モード共通で、先行specの実行は不要。

Javadocの記載を、この実行における期待値の根拠とする。
それが最新の業務仕様であると保証するものではない。
一般の制約順は安全 → キット基本 → Project Rules → 選択した仕様 → 実装。
期待値は選択した仕様だけから決め、Project Rulesは「どうテストするか」に限る。

## 参照範囲と保護

対象メソッド・クラスのJavadocを読み、必要に応じてインターフェース・親クラス、
引数/戻り値のDTO・enum、関連する公開メソッドのJavadocへ進む。
継承される契約やinheritDocの参照元を確認する。参照解決できない箇所を推測で補わない。
継承元と実装側の記載が矛盾する場合、記載順や実装に合わせて勝者を決めない。

関連箇所だけを選択し、全ソース・外部リンクの無条件な再帰読込みは行わない。
通常の実装コメント、メソッド名、条件式、定数を業務契約の代用にしない。
実装は呼出し方・依存関係・Mock準備の理解に使えるが、不足する業務期待値の根拠にはしない。

対象モジュールのsrcは既存のハッシュ保護に含まれるため、Javadocの編集も変更として検出する。
外部ソース等を根拠として使う場合は、ユーザーが許可したアクセス範囲内で、
prepare前に既存設定protectedPathsで保護されていることを確認する。
保護されていない外部資料は今回の根拠に採用せず、影響ケースをSPEC_UNKNOWNとして記録する。
必要な保護設定の追加は別の導入/保守作業で行う。UT実行中に設定を変更しない。
参照した版とprepareの基準値を照合し、異なれば読み直して新しい実行で扱う。

## ケース単位の判断

記載された条件から期待値を確定できるケースを生成する。
曖昧な条件、契約間の矛盾、Javadoc欠落、参照不能はケース単位でSPEC_UNKNOWN。
実装の戻り値・同じ計算式やProject Rulesの業務値から穴埋めしない。
一つの具体例だけから一般規則や未記載の境界を推定しない。
正常系が確定し異常系が不明なら、正常系だけ実行して異常系の不足を残す。
意味の弱いassertやダミーテストで未確定ケースを実行済みにしない。

生成できるケースは継続する。全件未確定ならprepareのフォルダにreport.mdを作り、
executeは呼ばず「未実行・未計測」とする。UNKNOWNをJUnitのFAIL/SKIPへ加算しない。
正当な契約不一致のFAILを消すために期待値を変更しない。
本番コード・Javadoc・既存UTを修正せず、private methodも直接呼ばない。

## report.md

既存の統合レポートを使い、新しい説明用JSONや別レポートは作らない。
根拠種別Javadoc、参照したファイル・クラス/メソッド（オーバーロードを識別するシグネチャ）・
行/タグ等の箇所、確認できた契約の範囲を記載する。
成功は集計し、不一致・未確定は固定IDと根拠を対応付けて個別記載する。
未確定には不足/矛盾/参照不能の理由と確認事項を示す。

不一致の観測事実は「Javadocの契約と実装の不一致」と表現する。
Javadocの陳腐化・誤記の可能性と、業務上どちらが正しいかの判断を区別する。
reviewの修正案は採用した契約に従う場合の案として示し、業務的な正解や検証済み修正と断定しない。

## 実行基盤

AIコマンド-Jはスクリプトprepareの-Javadocに対応する。
run.jsonのspecSourceはimplementation/document/javadoc。
-Jではspec=null、-Dではspecに解決済みパスを保存する。
設定schemaVersion=1を維持し、新しいプロジェクト設定は不要。
executeは既存どおりrun.jsonと生成UTを使い、Javadocの意味解析はAIが担当する。
旧run.jsonにspecSourceがない場合、coverageはimplementation、spec/reviewはdocumentとして解釈する。
旧成果物の書換えは行わない。

Javadocの品質基準・執筆ガイドは本変更の対象外で、別途整理する。
