# Project Rulesの設計と運用

## 責務と設定

Project Rulesは「このプロジェクトでどうテストするか」を追加する任意の設定。
キットはJava/JUnitの汎用基盤のまま、命名、Mock、除外、境界値の選び方、
ドメイン特有の検証方法、追加レビュー観点を導入先で定義する。
業務上の正しさを定義する資料ではない。

対象プロジェクトのut-kit.jsonにMarkdownファイルの配列を登録する。

```json
{
  "projectRules": ["rules/project.md"]
}
```

これは既存設定へ追加する項目の例であり、設定全体を置き換えるものではない。
schemaVersionは1を維持する。項目省略・null・[]は追加ルールなし。
相対パスは対象プロジェクト基準、絶対パスも使用可能。UTF-8の既存.mdファイルを指定する。
ディレクトリ、空文字、配列以外、重複パス、存在しないファイルはエラー。
設定済みファイルが読めない場合も黙って無効化せず、生成・実行を停止して理由を報告する。

複数ファイルの記載順は優先順位ではない。通常のutコマンドに引数を追加する必要はない。
公開キットには rules/project.example.md だけを置き、実際の rules/project.md は導入先に置く。
AIは実プロジェクトの規則・名称・秘密情報を公開キットへ転載しない。

## 優先順位と矛盾

一般の操作・テスト方針は、安全制約 → キットの基本ルール → Project Rules →
業務仕様 → 実装の順で制約を確認する。これは、業務期待値を上位のテスト方針で
上書きできるという意味ではない。各資料の責務を分ける。

| 判断 | 根拠と扱い |
| --- | --- |
| 安全・変更範囲 | 実行環境とキットの制約が最優先。本番コード、既存UT、設定、仕様、Rulesを実行中に変更しない。Git操作は禁止 |
| テスト方法 | キットの必須制約内でProject Rulesを適用。未記入部分は汎用方針。依存Mockの既定方針など、明示された拡張可能部分を具体化できる |
| spec/reviewの期待結果 | -Dの業務仕様 → Project Rules → 実装の順に照合する。ただし期待値のauthoritative sourceは-Dだけ。後二者を仕様不足の代替情報源にしない |
| coverageの期待結果 | 実装を解析して入力と固定期待値を決める。Project Rulesはテスト方法にだけ適用。仕様やRules内の業務値を期待値に採用しない |

spec/reviewでは、仕様から一意に決まらない期待値をProject Rulesや実装で補完せず、
SPEC_UNKNOWNとして記録し、確定できるケースは継続する。業務仕様に反するルール内の
期待値は採用せず、仕様を使った理由を記録する。Rulesだけが示す業務値も同様に採用しない。

private method直接テスト、対象自体のMock化、自己比較による期待値、実DB・外部サービス依存、
正当なspec FAILを通すための期待値変更・無効化は、Project Rulesでも許可できない。
固定ケースID、Test末尾のクラス名、既存UTとの分離、正確な実測報告も必須。
追加レビューは既存モードの責務を変えない。specで原因分析・修正案を追加せず、
reviewで追加分析を行う。coverageで仕様適合を判定しない。

明確な上位制約との矛盾は該当ルールを不採用にして根拠を記録する。
同じ責務・同じ優先度のルール同士で両立できない場合は、記載順で勝手に勝者を決めず
RULE_CONFLICTとして規則ID、矛盾、影響ケース、確認事項を記録する。
そのケースの生成は保留し、独立したケースは継続する。全ケースが保留ならexecuteを呼ばず、
未実行・未計測と報告する。RULE_CONFLICTをJUnitのFAIL/SKIPへ変換しない。
業務仕様自体の不足・矛盾による期待値未確定は従来どおりSPEC_UNKNOWNへ記録する。

## 読み込みと適用証跡

1. AIは各ut実行の開始時に設定を読み、登録ファイルの存在と可読性を確認する。
2. 各ファイルの見出し・適用範囲を調べ、全体共通ルールと対象モード・クラスに関係する節を読む。
   未分類・範囲不明の節は関連なしと即断せず内容を確認する。全文の無条件読込みを要求しない。
   外部リンクを自動的に再帰読込みする仕組みではなく、必要なファイルは明示的に登録する。
3. prepareが返すrun.jsonとproject-rules.jsonのパス・ハッシュを確認し、その版を使って生成する。
   事前に読んだ版と違えば読み直す。変更後に同じ実行を続けず新しいprepareから開始する。
4. AIはUT生成・モードに応じたレビューに適用し、rules-application.jsonへ証跡を残す。
5. executeは全登録ファイルを保護対象に含めて開始前・終了後に変更検出する。
   登録・ハッシュ検査は適用内容の妥当性の自動判定ではない。

rules-application.jsonはAIが作成する。未設定時はstatus=NOT_CONFIGURED、配列は空。
設定時は以下の項目を持つ。本文全文や秘密情報を複写せず、参照箇所と判断を記録する。

- status: APPLIED / PARTIAL / NOT_CONFIGURED（矛盾や未読の影響が残ればPARTIAL）
- files: path、sha256、readSections、omittedSectionsとその理由
- applied: ruleId、source、section、対象、mode、適用内容、UTケースIDまたはレビュー箇所
- rejected: ruleId、source、section、不採用理由と優先した制約
- conflicts: status=RULE_CONFLICT、規則ID群、影響ケース、理由、確認事項
- excludedTargets: 対象、除外理由、規則ID

report.mdに適用概要と両JSONへのリンクを載せる。review.mdでは追加観点の結果と規則IDを対応させる。
スクリプトはrules-application.jsonの意味を検証しない。存在だけで適用済みと判定しない。

除外は実行前に要求された対象と実際の対象を分けて報告する。クラス全体の除外はprepareのTargetsへ
含めず、除外一覧を残す。全クラス除外ならprepare/executeを呼ばず未実行理由と一覧を回答する。
クラス内の一部メソッドを除外してもJaCoCoのクラス単位分母は減らさず、未カバー理由を説明する。
除外によって元の要求範囲が100%検証されたと報告しない。

## 拡張余地と限界

複数ファイルと節の適用範囲により、関連部分を選択して読める。将来の索引・モード別選択は
この参照証跡を維持したまま拡張できる。現状はAIによる関連性判断で、ルールDSLや自動lintではない。
ハッシュは内容全体に対する変更検出であり、本文の一括コンテキスト投入や書込み禁止ではない。
外部ファイルへのアクセス権を与える機能ではなく、実行環境の権限に従う。
