# UT自動化コマンド

## Git操作は人間が担当する

このキットの導入・実行・保守では、Git操作を必ず人間が行う。AIはgitコマンドを実行しない。status/diff/log等の読み取り、init/clone/fetch/pull、add/commit/push、ブランチ・履歴操作、Git設定変更を含む。特にAIによるcommit・pushは禁止する。GitHub等のAPI・連携ツール・別スクリプトへ迂回して同じ操作を代行しない。

Git操作が必要な場面では、AIは変更ファイル・検証結果・必要な手順を説明して人間へ引き継ぐ。導入やutの依頼をGit操作の許可と解釈しない。変更確認にはファイル集合とSHA-256を使う。Git操作を実行するための承認要求を出して代行する運用にもせず、人間が実行する。

このファイルを読み込んだ時点では待機する。ユーザーが実行指示として入力したutを処理する。説明用の例は実行しない。これはAIへのコマンドで、OS上のCLIではない。

## 構文

```text
ut -P "<対象モジュールの絶対パス>" -coverage <完全修飾クラスまたはパッケージ.*> [-O "<出力ルート>"]
ut -P "<対象モジュールの絶対パス>" -spec <対象> -D "<仕様参照パス：ファイルまたはディレクトリ>" [-O "<出力ルート>"]
ut -P "<対象モジュールの絶対パス>" -review <対象> -D "<仕様参照パス：ファイルまたはディレクトリ>" [-O "<出力ルート>"]
```

-Pと機能1個、対象は必須。spec/reviewは-D必須。相対の-D/-Oは-P基準。出力先は-Oが設定ファイルoutputRootより優先する。設定は対象ルートのut-kit.json。対象の曖昧さを推測して埋めない。仕様不足は後述のSPEC_UNKNOWNとして扱う。権限が必要なら実行環境の承認手続きを使用する。

機能に順序はない。coverageは実装を解析し、観測可能な振る舞いを確認するための具体的な入力と固定期待値を事前に決める。実行した本番コードの戻り値をそのまま期待値生成に利用してはならない。`assertEquals(service.calculate(x), service.calculate(x))` のような自己比較や、実測値を保存して同じ実行の期待値にする方法は禁止する。業務仕様、過去の仕様UTやレビューを期待値の根拠にしない。spec/reviewは共通の仕様ベースUT生成方針で、どちらも独立して生成・実行する。reviewだけ原因分析と修正案を追加する。reviewがspecの事前実行を要求してはならない。既存の生成UTの再利用はユーザーが明示した場合だけ、対象・仕様・ソースのハッシュと根拠を確認して行う。

## Project Rulesの自動適用

各utの開始時にut-kit.jsonのprojectRulesを確認する。未設定・null・[]なら汎用方針のみ。
設定時はキットのdocs/project-rules.mdを必ず読み、その優先順位・選択読込み・矛盾処理・証跡形式に従う。
登録ファイルの共通規則と対象モード・クラスに関連する節を読み、UT生成とモードに応じたレビューへ適用する。
存在しない・読めない登録ファイルを無視して実行しない。コマンドごとのルール指定は不要。
全体の制約は安全 → キット基本 → Project Rules → 業務仕様 → 実装。
期待結果の照合順は-D業務仕様 → Project Rules → 実装だが、spec/reviewの期待値根拠は-Dのみ。
Project Rulesは業務仕様を上書きせず、不足を補完しない。未確定はSPEC_UNKNOWNで部分継続する。
上位制約に反する規則は不採用と記録し、同順位の解消不能な矛盾はRULE_CONFLICTとして
影響ケースの生成だけを保留する。全件保留なら未実行・未計測としexecuteしない。
対象の除外は事前に要求範囲と実行範囲を分けて報告し、カバレッジの分母を恣意的に減らさない。
全クラス除外ならprepareも呼ばず理由と対象一覧を回答する。

prepare後はproject-rules.jsonと読んだ版のハッシュを照合し、rules-application.jsonに
参照節、適用規則とケースID、不採用・未読理由、矛盾、除外対象を記録する（未設定時もNOT_CONFIGURED）。
UT生成後・レビュー後に実際の成果物と記録を照合し、適用したと断定するだけで済ませない。
Rulesは実行中に変更しない。設定変更・Rules編集は別の導入/保守依頼として扱う。

## 仕様参照パスと関連資料の選択

-Dはファイルまたはディレクトリを受け付ける。存在しないパスやアクセス不能で資料を調べられない場合は、その入力・環境上の問題を報告する。

ディレクトリの場合は配下を再帰探索する。まずファイル一覧、名前、目次、見出し、対象クラスの責務・API・業務用語との一致を調べる。関連候補の必要な部分から読み、参照関係をたどって仕様根拠を確認する。全ファイルの本文を無条件にコンテキストへ読み込まない。クラス名の文字列一致だけで関連性を決めず、基本設計・API・業務ルール間の関係も考慮する。

spec-sources.jsonに、探索したルート、再帰探索の完了/部分実施、実際に読んだファイルと見出し、対象との関連理由、未読・除外範囲と理由、読めなかった形式・アクセス制約を記録する。全探索候補の本文や機密データを転記しない。仕様ファイルの相互参照が指定ルート外へ出る場合は範囲外として記録し、ユーザーが許可した参照範囲を越えて勝手に読む前提にしない。

スクリプトは参照ディレクトリ内の全ファイルを変更検出用にハッシュ化するが、これはAIが全資料の内容を読んだという意味ではない。ディレクトリ内に出力先を置かない。レポートでは実際に読んだ仕様だけを根拠として示す。

## 仕様不足・矛盾：SPEC_UNKNOWN

spec/reviewで仕様から期待値を一意に決められないケースは、実装から期待値を補完しない。固定ケースIDを付け、spec-unknown.jsonに次を記録する。

- status: SPEC_UNKNOWN
- 対象クラス、入力条件・検討したケース
- 参照した仕様パス・箇所、判断できない理由（不足・矛盾・読取不能等）
- 決定できない期待値、ユーザーに確認したい事項

影響を受けない生成可能なケースは継続し、ユーザーの回答待ちだけを理由に全体を停止しない。共通の前提が不明なら影響を受けるケースをまとめて記録し、無関係なケースまで未知扱いにしない。回答がない場合に実装値を採用したり、任意の解釈を仕様の決定として扱ったりしない。

SPEC_UNKNOWNは仕様評価上の状態であり、JUnitのFAIL/ERROR/SKIPではない。期待値不明のテストをダミーのassertや@Disabledで作らない。実行件数とは別に未生成ケースの件数・一覧を報告する。spec-unknown.jsonは該当なしでも空配列で保存する。既存summary.jsonのテスト状態は変更せず、report.mdに「テスト実行結果」と「仕様評価：未確定ケースあり」を分けて記載する。

すべてのケースがSPEC_UNKNOWNなら、prepareで作ったフォルダへ参照資料・未知ケース・未実行理由・概算トークンとreport.mdを保存し、executeは呼ばない。0件成功やcoverage 0%とは報告せず「テスト未実行・カバレッジ未計測」とする。reviewも未知ケースについて原因を実装不備と断定したり、根拠のない修正案を出したりしない。

## 実行手順

1. 導入記録ut-kit-setup.md、ut-kit.json、対象ソース、必要な関連コード、ビルド設定、適用されるAGENTS.mdを読む。通常UTは保持する。未導入ならsetup.mdに沿って導入調査を行い、実行中にpomを場当たり的に変更しない。
2. 対象を具体的なクラス一覧へ解決する。パッケージ.*は下位を含む。初版の標準ソース/単独Mavenモジュール制約を確認する。Mock依存先・テストコードを分母に加えない。仕様参照パスを後述の手順で探索し、対象に関連する仕様を選んで読む。期待値が一意に決まらないケースはSPEC_UNKNOWNに記録し、生成可能なケースは継続する。
3. このコマンドの開始境界とトークン累計を可能な範囲で記録する。キット配置先のscripts/Invoke-UtRun.ps1をprepareで呼ぶ。Targetsには解決したクラス配列、Mode/Spec/Outputを渡す。実行フォルダと元のソース/仕様のハッシュが作成される。
4. 実行フォルダjava/へJUnit5のUTを生成する。公開入口のみを検証し、依存先は既定でMockitoでMock化する。Project Rulesに実体使用の指定がある純粋なMapper等はその方針を適用できるが、実DB・外部サービス接続は禁止。テスト対象自体の振る舞いをMock化しない。生成クラス名はTestで終わり、パッケージを明記する。すべてのケースに実行順非依存の固定IDを付け、表示名、アサーション、各ケースのsystem-outにもIDと入力/期待値を残す。割引率・金額等の期待値は個別の固定値とし、本番と同じ計算式で期待値を作らない。
5. spec/reviewの各UTには狙いと仕様箇所をコメントで示す。正常、異常、境界、丸め等を仕様から抽出し、仕様に根拠のない期待値でカバレッジを埋めない。仕様と期待値の対応表を作る。private直接呼出し、可視性変更、実DBや外部サービス依存は禁止。
6. スクリプトexecuteを実行する。FAILでも別にJaCoCoが生成される。test.log、coverage.log、Surefire XML、JaCoCo XML、summary.json、change-check.jsonを実際に読む。スクリプトの成功だけで仕様適合と断定しない。固定IDが全件一意でXMLから追えることを確認する。全件スキップ、0件、コンパイル失敗を成功扱いしない。
7. UT自身の不備は修正する。ただし再試行はprepareで新しい実行IDを作り、修正したUTを新フォルダに保存して実行する。前回フォルダを書き換えない。最終レポートに試行IDと理由を列挙する。正当なFAILを消すため期待値を書き換えたり、skip/disableしたりしない。
8. 最終report.mdを作り、reviewの場合はreview.mdも作る。coverageの目標はLine 100%、Branchは別報告。未達や未計測を隠さず、未カバー箇所と理由を説明する。対象に内部クラス等が含まれる場合は明示して集計設計を確認し、暗黙に範囲を縮めない。
9. 相対リンク、レポートの数字とXML、固定ID、保護対象ハッシュ、PowerShellコマンド構文を確認する。元ログを会話全文で埋めず、必要な証跡だけを残す。最終回答に今回の絶対パスを示す。

## レポート

report.mdの構成:
1. コマンド、モジュール、対象一覧、仕様、実行IDと再試行ID、参照範囲。Project Rulesの適用概要、project-rules.jsonとrules-application.jsonへのリンク、除外・不採用・RULE_CONFLICTを記載。
2. UT一覧、固定ID、入力、固定期待値、spec/reviewは仕様根拠とspec-sources.jsonへのリンク。
3. 実行方法、件数、成功/失敗/エラー/skip、ログ・XMLリンク。掲載するMavenの-P/-D引数は引用符で囲む。実行時の記録と再実行例を区別し、再実行では未使用IDを指定する。
4. 対象クラス別Line/Branchのcovered/missed/割合。分母0はN/A。欠けたクラスは未計測。
5. 不一致ケースと期待/実際、仕様根拠。コンパイル・環境・UT不備・実装不一致・仕様不足を区別する。
6. reviewのみ、原因、ソース位置、根拠、確度、固定ID、修正案。修正を本番に適用しない。未実行の修正案を検証済みと呼ばない。
7. 制約・未完了・保護対象の変更確認。spec/reviewはSPEC_UNKNOWNの件数・ケースID・理由・確認事項とspec-unknown.jsonへのリンクを実行件数とは別に示す。
8. 末尾にトークン概算。review.mdは同じ項目を参照し二重集計しない。

review.mdには分析を記載する。specで詳細な修正案を生成しない。スクリプトが出すexecution.mdは機械集計であり、このレポートを代替しない。人間がUT→仕様→失敗→原因を追えるよう、プロジェクト外の-Oでも相対パスを正しく算出する。

## トークン概算

現在のチャットだけのローカルtoken_countが取得可能ならinfo.total_token_usageを使用する。CODEX_THREAD_IDなどの確実な識別情報でログを特定し、他のチャットや認証情報は集めない。入力指示より前の最後の有効な累計を基準に、最終レポート直前の累計との差分を取る。境界不明なら最初に取得できた累計を使い、初期処理が含まれないと明記する。

input_tokens、うちcached_input_tokens、output_tokens、total_tokens、参考reasoning_output_tokensを記録する。内数を再加算しない。時刻、チャットID、実行ID、基準と終了の数値、差分、未計測範囲をtoken-usage.jsonへ保存する。最終取得後の記述・確認・回答は含まれない可能性があるため概算とする。再試行は同一コマンドの計測区間に含める。累計の減少や欠損は未取得理由として残し、ゼロや文字数推定で埋めない。ログ全文は配布しない。使用量から請求額を断定しない。

## 変更境界

本番コード、既存UT、仕様、Project Rules、ut-kit.json、pom等ビルド設定は実行中に変更禁止。許可するのは今回の実行フォルダ内の生成・レポートだけ。導入時の変更とは分ける。Git操作、公開、既存成果物の削除、README変更、samples更新はutに含めない。キット自身のファイルは開発依頼の範囲で修正できるが、Git操作を人間に限定するルールはキットの保守にも適用する。
